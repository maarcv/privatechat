# 060 — Reproducible builds, signing and published hashes

Status: draft
Phase: 6
Related ADRs: 0017, 0041
Depends on: 034-docker, 040-uniffi, 041-desktop-bridge, 042-connection-host, 050-desktop-mvp, 051-android-mvp, 052-ios-mvp
Blocks: 061-threat-review, 062-security-docs, 063-beta, 064-public-release
Human reviewer: Marc Vilardebó · Accepted on: —

## Context

A client whose code a server or a store could change silently would undo the model: `docs/spec.md` §2 answers a malicious server with "open source + reproducible builds", and §8 "Code integrity" asks for reproducible builds with published hashes on every platform. This spec defines how a release is built, how it is signed, and how anyone can check that the published artefacts come from the tagged source. The human reviewer decided on 2026-09-27 that the signing keys live on hardware tokens held by the human owner, and that CI builds while a local machine signs (`docs/audit-log.md`, "Phase 6 drafts", Q14); that the beta's Android build is the owner-signed APK sent by private link, Google Play being decided by spec 064-public-release ("Audit O", O-Q1); that a spec 064 covers the public release (O-Q4); that the owner rebuilds the Windows artefacts on a Windows virtual machine of his own before signing them, and that releases leave Windows out until it exists (O-Q5); and that the signed manifest of every public release is logged in Sigstore Rekor (O-Q6).

Not every artefact can be bit-for-bit reproducible. The App Store re-signs and encrypts every iOS binary. A macOS or Windows signature cannot be removed back to the original bytes (measured on 2026-09-27: the linker already ad-hoc signs a Mach-O, and `codesign --remove-signature` leaves a file of another size), so those binaries are compared after stripping the signature from both copies. Installers that contain signed binaries are rebuilt around them. And macOS and Windows artefacts cannot be rebuilt in a Linux container, so only their own build hosts can compare them: the owner's Mac and the owner's Windows virtual machine before signing, and a third party with those hosts afterwards.

**In plain words.** The project builds each version twice in its CI and once more on the owner's own computer, and signs only when the three agree byte for byte. It then publishes a list of the files' fingerprints (hashes), signed with a key on a small hardware device the owner keeps, which needs a touch for every signature, with a spare device kept elsewhere. Anyone can rebuild the server, the Linux app and the Android app in a container and get the same files; the macOS, Windows and iPhone apps can be checked only in part, and the spec says which part. The key's fingerprint is published in places that do not depend on GitHub, the first check needs nothing from the repository, and every public release is written into a public log that nobody can rewrite, so that taking over the project's GitHub account and web site is not enough to pass off a changed app, even to a single person.

## Requirements

**Tags and inputs**

- R1 A release MUST be built only from an annotated tag signed with a release key of R5 (`sk-ssh-ed25519`, `git tag -s` with `gpg.format = ssh`), of one of three forms: `vX.Y.Z` (a public release, spec 064-public-release), `vX.Y.Z-beta.N` (a beta build, spec 063-beta) and `vX.Y.Z-rc.N` (a CI trial, never distributed, R7). The tag is on the default branch (`mvp` until the first release, then the default branch the owner names) or on a branch `release/vX.Y` cut from a `-beta.N` or `vX.Y.Z` tag, whose fixes are forward-ported to the default branch (`git merge-base --is-ancestor`). A tag whose build failed is never moved or reused: the next PATCH or `N` follows. GitHub tag-protection rulesets MUST cover `v*` and `review-*`. The CI jobs of R9 MUST run only for tags matching `v*`, re-fetch the tag (`+refs/tags/$T:refs/tags/$T`), fail unless `git cat-file -t $T` is `tag`, and verify it with `git verify-tag` against the `.github/allowed_signers` of the previous release tag, that is the highest-version `v*` tag that is an ancestor of `$T` (the tag's own copy for the first release, a documented residual), checking the exit status and never the output text (measured on 2026-09-27: a wrong key prints "Good" and exits 1). This CI check stops a pusher without admin rights; the check that counts is the owner's, in R6, against a signers file kept on his own machine. A new release key is first added to `allowed_signers` in a release signed by a key already listed.
- R2 Every build MUST be deterministic in its inputs:
  - the toolchains pinned: `rust-toolchain.toml`, the Node version of `.nvmrc`, the Android SDK, NDK and build-tools, the Xcode version, the MSVC toolset and the Windows SDK; base images pinned by digest (spec 034-docker R1) and Debian packages from `snapshot.debian.org` at a fixed date;
  - every lock file (the root, `crates/host/`, `bindings/uniffi/`, `clients/desktop/src-tauri/`, `pnpm-lock.yaml` with `ignore-scripts`, Gradle's verification metadata, `Package.resolved`) and `cargo build --locked`;
  - the tools that bundlers download at bundle time (Tauri's linuxdeploy, AppRun and its plugins, NSIS) committed with their SHA-256 under `vendor/bundler/` and placed in the bundler's cache before it runs;
  - `CARGO_INCREMENTAL=0`, and `--remap-path-prefix` of both the repository root and `$CARGO_HOME` to fixed names, set by `scripts/release_env.sh` since `.cargo/config.toml` cannot expand variables (measured: a different `CARGO_HOME`, or a path dependency outside the workspace, changes the binary without them; `trim-paths` is unstable on 1.98.1);
  - `SOURCE_DATE_EPOCH` set to the tag's commit time, for the tools that read it (buildkit, `dpkg-deb`, the zip and NSIS steps of R3); rustc and `cargo build` do not read it (measured);
  - `libsodium-sys-stable` without its `optimized` feature and with no `CFLAGS` in the environment, since that feature builds with `-march=native`;
  - the beta flag of spec 063-beta R3 compiled from the tag's `-beta.N` suffix, together with an expiry 90 days after the tag's time after which the app shows a blocking notice to install a newer build (a local rule, not a remote switch), and the "RC" flag compiled from `-rc.N` (R7), so that beta and rc builds are as reproducible as public ones and cannot pass for them;
  - the versions derived from the tag alone: the displayed version is the tag; the Android `versionCode` is `(((X*100+Y)*100+Z)*100 + C) * 10 + A`, with `C` = `N` (0..=29) for `-rc.N`, 30 + `N` (30..=89) for `-beta.N` and 99 for `vX.Y.Z`, and `A` the ABI index of spec 051-android-mvp R7, so that every later tag installs over an earlier one and a public release over its betas; the iOS `CFBundleVersion` is the single integer `((X*100+Y)*100+Z)*100 + C` and `CFBundleShortVersionString` is `X.Y.Z`, since Apple accepts at most three period-separated integers;
  - no network access after dependency resolution, the vendored libsodium of spec 042-connection-host R15 included.
- R3 The job `release` MUST build each artefact twice, with the same pinned toolchain image or version and a different host, user, build path and `CARGO_HOME`, and fail unless the two are byte-identical; it writes `unsigned-hashes.txt`, one line `<sha256>  unsigned/<name>` per artefact, and uploads that file alone as a run artefact, with a retention of 1 day, so that no build of a beta can be downloaded from the run. The artefacts are:
  - the server's OCI image, built with buildkit, `SOURCE_DATE_EPOCH` as a build argument, `rewrite-timestamp=true`, `--no-cache`, `--provenance=false` and `--sbom=false`, compared by its per-platform manifest digest (measured identical with these flags and different without them), and its binary as spec 034-docker R1 builds it;
  - the desktop's unsigned Linux AppImage and `.deb`, the `.deb` repacked by `dpkg-deb --root-owner-group` with sorted entries and file times clamped to `SOURCE_DATE_EPOCH` (Tauri's own `.deb` records file times and directory order, source-read on 2026-09-27);
  - the desktop's unsigned macOS `.app`, hashed as the zip made by `touch -h` of every file to `SOURCE_DATE_EPOCH`, then `LC_ALL=C sort` of the file list and `TZ=UTC zip -X -y -D -@` (measured identical);
  - the desktop's unsigned Windows executable and NSIS installer, linked with `/Brepro` and with no PDB path, and the installer built with file times normalised (`SetDateSave off`);
  - the unsigned Android APK of each ABI (spec 051-android-mvp R7), with `dependenciesInfo { includeInApk = false; includeInBundle = false }`, and, for a `vX.Y.Z` tag, the unsigned Android App Bundle that spec 064-public-release R4 uploads to Google Play;
  - the unsigned iOS `.app` of `xcodebuild archive` with `CODE_SIGNING_ALLOWED=NO`, hashed as the macOS zip is.
  A differing byte fails the release; the only exceptions are the residuals of R4.
- R4 These MUST be the residuals listed with every release (Security): the iOS app as installed from the App Store, which Apple re-signs and encrypts and whose `Info.plist` carries the build Mac's `BuildMachineOSBuild` and `DTXcodeBuild`, so that only the unsigned archive is compared; the macOS and Windows artefacts, which a third party can compare only on those platforms' own build hosts; the libsodium binary of spec 042-connection-host R15 that the Windows desktop links, listed as an input and not rebuilt; and the first release's tag, checked against its own signers file (R1).

**Keys and signing**

- R5 A signing key MUST NOT exist as a CI secret or in any file in the repository, the CI runners or a cloud service (Q14), and every key MUST have a backup enrolled when the key is created. Each key and its backup MUST need a physical touch and a PIN or user verification for every signature: `sk-ssh` keys created with `-O resident -O verify-required`, PIV keys with PIN policy "always" and touch policy "always". The backup tokens are kept sealed in one tamper-evident place that `docs/release-keys.md` names, and the seal is inspected at each release. The keys are:
  - the release key: an `sk-ssh-ed25519` key and its backup, which sign tags (R1) and `SHA256SUMS` with `ssh-keygen -Y sign -n privatechat-release`; rc manifests are signed under the namespace `privatechat-rc` (R7);
  - the Android signing key, generated once on a machine booted from read-only live media with no disk, imported into two tokens, and the generating material destroyed, with a signed record of that in `docs/release-keys.md`; used through PKCS#11 as `java -Djava.security.properties=<file naming SunPKCS11 and its config> -jar apksigner.jar sign --ks NONE --ks-type PKCS11` (measured: the `--provider-class` form fails on JDK 22), with signature schemes v2 and v3;
  - the Apple distribution and Developer ID identities, on a smart card that CryptoTokenKit exposes to `codesign` and Xcode; their backup is a second certificate of the same team, on a second card, with its own fingerprint, since a certificate key made on a card cannot be copied;
  - the Windows Authenticode certificate, from an authority that ships it on a physical token (the CA/Browser Forum's code-signing rules require a hardware module since 2023, and several authorities now sell only cloud modules, which R5 forbids), renewed within its validity (currently at most about 460 days), used with `osslsigncode` and the token's PKCS#11 module; its backup is a second certificate from the same authority;
  - the Google Play upload key and the Android code-transparency key of spec 064-public-release R4, two separate keys, each on a token with a backup; `docs/release-keys.md` also lists the Google-generated app-signing certificate, which MUST differ from the Android signing key's.
  `docs/release-keys.md` MUST list every key and backup with its fingerprint (`SHA256:…`), its creation date and, for a certificate, its history; `.github/allowed_signers` MUST hold the release keys' public halves with `namespaces="git,privatechat-release,privatechat-rc"`, and `check_s060_t05_r05_keys` fails when the two files disagree. A key is replaced only by a statement signed by a key that is still listed, published beside the release as `ROTATION-<date>.txt` with its signature; a retired key's entry keeps a `valid-before` date and the list of `SHA256SUMS` it legitimately signed, and `verify_release.sh` rejects any other manifest signed by it. When a key is compromised: the Android key is rotated with a v3 lineage signed with `apksigner --rotation-min-sdk-version 28` that removes the old signer's capabilities (the v2 block staying signed by the old key for devices below that level, which the notice says), F-Droid's `AllowedAPKSigningKeys` is changed before the rotated tag ships (spec 064-public-release), and the owner publishes a notice through the channels he controls: the landing, the GitHub release, the F-Droid description in the fdroiddata recipe (spec 064-public-release R3), and the signed `ROTATION-<date>.txt`. A replacement key follows the ceremony of the first: generated on a live boot, imported into two tokens, with a signed record.
- R6 Signing MUST happen on the owner's machines, outside GitHub: a dedicated or live-booted macOS machine and a Windows virtual machine of his own (O-Q5), with `scripts/sign_release.sh <tag>` run from the owner's own verified copy of the script, never from the checkout it verifies. It:
  - verifies the tag against an `allowed_signers` file kept on the owner's machine (or the tokens' public keys held offline) before it runs anything from the checkout, and checks out that tag;
  - rebuilds locally, in the pinned container of R8, every artefact a Linux container can rebuild, on the macOS host the macOS and iOS artefacts, and on the Windows virtual machine the Windows artefacts, and refuses to sign any line of `unsigned-hashes.txt` it did not rebuild or that differs from its rebuild; without the Windows virtual machine the release leaves Windows out (the last bullet); the iOS archive it signs is its own local one, never CI's;
  - announces how many touches it will ask for, and aborts on any extra request;
  - signs the APKs (R5), and `codesign`s, notarises and staples the macOS app, then rebuilds the macOS zip and dmg around the signed app; on the Windows virtual machine, with the token attached to it, signs the Windows executable with `osslsigncode`, rebuilds the NSIS installer around it, which signs the uninstaller during its build, and signs the installer, three signatures that the announced touch count names (Tauri's installer embeds and signs the executable and the uninstaller, so a signed installer is never the unsigned one plus a signature);
  - for a `vX.Y.Z` tag, builds the Play bundle of spec 064-public-release R4: `bundletool add-transparency` with the code-transparency key on its token, then the bundle signed with the upload key through PKCS#11, both counted in the announced touches, and a `signed/` line for it in `SHA256SUMS`; the owner uploads it to the Play Console by hand;
  - for a `vX.Y.Z` or `-beta.N` tag, signs the iOS archive with the distribution identity, exports the IPA and uploads it to App Store Connect with Transporter; never for `-rc.N`;
  - writes `SHA256SUMS`: a first line `# <tag> <full commit SHA>`, then `<sha256>  unsigned/<name>` and `<sha256>  signed/<name>` for every artefact that shipped, the libsodium input of R4 and the iOS archive; prints its hash for the owner to read and compare with the local rebuild's output; signs it (R5) into `SHA256SUMS.sig`; for a `vX.Y.Z` tag, logs `SHA256SUMS` and its signature in Sigstore Rekor right away, before any upload, so that the `verify` job and every later check find the entry (spec 064-public-release R1 records it in the "Public release" row);
  - verifies every signature on a second machine of the owner's before upload;
  - uploads the signed artefacts, `SHA256SUMS` and `SHA256SUMS.sig` to a draft GitHub release of the tag, which it always leaves a draft: publishing is a manual step of the owner, only for a `vX.Y.Z` tag, after the job `verify` is green and the gate of spec 064-public-release; for a `-beta.N` tag the owner also copies the files to the private file host of spec 063-beta R2.
  It makes no network request other than to GitHub, Apple's notary and timestamp services, App Store Connect, the RFC 3161 timestamp service of the Windows authority, the private file host of spec 063-beta R2, the Play Console (by hand, for a `vX.Y.Z` tag) and, for a `vX.Y.Z` tag, Sigstore Rekor. The App Store Connect API key and every other non-signing credential are held in the owner's keychain alone. A platform whose key or build host is unavailable may be left out of a release; `SHA256SUMS` then lists only what shipped, and nothing is uploaded before every key present has signed.
- R7 The signed APK MUST be the rebuilt unsigned APK plus its signature block: the CI job `verify` rebuilds the APK and checks it with `apksigcopier compare` against the signed one. F-Droid's own rebuild and its `AllowedAPKSigningKeys` are spec 064-public-release's. An `-rc.N` build MUST show a visible "RC" mark (R2), MUST be signed only with a test Android key listed as such in `docs/release-keys.md` and left unsigned on macOS and Windows, and its manifest only under the namespace `privatechat-rc`, so that no rc build carries a production signature.

**Checking a release**

- R8 A third party MUST be able to check a release in two steps. First, with nothing from the repository, two commands printed in the beta letter (spec 063-beta R4) and in the review report (spec 061-threat-review R8), which need only the `SHA256:` fingerprint published out of band (R10): `ssh-keygen -Y check-novalidate -n privatechat-release -s SHA256SUMS.sig < SHA256SUMS` (the namespace `privatechat-rc` for an `-rc.N` tag), which MUST exit 0 and print the signing key's `SHA256:` fingerprint, compared by eye with the published one; then `grep '^[0-9a-f]\{64\}  signed/' SHA256SUMS | sed 's#  signed/#  #' | shasum -a 256 -c` in the folder of the downloaded files, which skips the header line and the `unsigned/` and `input/` lines. Second, after checking that the clone's `HEAD` is the commit that the manifest's first line names, `scripts/verify_release.sh <tag or folder> <fingerprint>…` from that commit, which: takes the files from the GitHub release, from a download URL, or from a local folder holding them with `SHA256SUMS` and its `.sig`; picks the namespace from the tag's suffix; accepts several fingerprints (a key and its backup) and gets the public key from the `.sig` or from `.github/allowed_signers` at the tag, refusing one whose `ssh-keygen -lf` fingerprint is not among its arguments; checks the manifest's first line against the tag and its commit; for a `vX.Y.Z` tag, checks that the manifest's hash is in Sigstore Rekor (O-Q6); rebuilds, in the pinned container of `deploy/release/Dockerfile`, the server image and binary, the Linux desktop artefacts and the unsigned APKs, and compares them; checks every signed APK with `apksigcopier compare`; on a macOS host rebuilds the macOS app and compares both copies after stripping their signatures, and checks the Team ID and certificate fingerprints of `docs/release-keys.md` with `codesign --display --verbose`; on a macOS host with the pinned Xcode also rebuilds the unsigned iOS archive and compares it, which a Linux host reports `unchecked`; on a Windows host rebuilds the Windows executable and compares it after `osslsigncode remove-signature`; prints the channel (`release`, `beta` or `rc`), with a warning for the last two, and, per artefact, `match`, `MISMATCH` or `unchecked`, exiting non-zero on any mismatch.
- R9 The CI MUST have two jobs, both on `v*` tags only, with `permissions: contents: read`, every Action pinned by commit SHA and no secret: `release` (R3), and `verify`, started by the owner through `workflow_dispatch` once `sign_release.sh` has uploaded (a draft release triggers no workflow), with two inputs, the tag and a download URL (the private file host of spec 063-beta R2 for a beta, a time-limited link for an rc or a public release), which runs `verify_release.sh` on a third runner over the files it downloads, checked against the signed `SHA256SUMS`, with the fingerprints written in the workflow; the job never reads a draft release; for a beta, the run's URL goes in the "Start" row of spec 063-beta. `.github/CONTRIBUTING.md` MUST describe cutting, signing and verifying a release, including the macOS OpenSSH that supports security keys (Homebrew's, or `SSH_SK_PROVIDER` and `gpg.ssh.program`).
- R10 The release key's fingerprint MUST be published outside GitHub and the landing's host: in the external review report as the reviewers or the programme publish it on their own site (spec 061-threat-review R8), in the letter to beta testers, on paper or in person (spec 063-beta R4), in F-Droid's app description once the app is there (spec 064-public-release R3), and in the apps' Help screen (spec 056-chat-screens R18), which serves only to check later downloads from an install already verified. The owner derives the fingerprint he publishes from the token itself (`ssh-keygen -K` or an offline copy of the public key) and compares it with `docs/release-keys.md` before publishing.
- R11 In the pull request that marks this spec `accepted`, the sentences about release signing in CI MUST be replaced by "CI builds; the owner signs on a local machine with hardware keys (spec 060-reproducible-builds)": in the architecture skill ("release signing happens in CI with the offline key"), the kotlin skill ("release signing happens in CI"), the swift skill ("… in CI with the offline certificate") and the typescript-svelte skill ("… in CI with offline keys"); and `docs/spec.md` §8 "Code integrity" MUST name the hashes of the unsigned and signed artefacts, the signed manifest and the residuals of R4, and §11 the files of the Interface.

## Limits

| Input | Range | Out of range |
| --- | --- | --- |
| A release tag | `vX.Y.Z`, `vX.Y.Z-beta.N` or `vX.Y.Z-rc.N`, annotated, signed by a key of the previous release's `allowed_signers` | the jobs refuse to run |
| `versionCode` channel `C` | rc 0..=29, beta 30..=89, release 99 | no tag with a higher `N` |
| Run artefacts | `unsigned-hashes.txt` alone, kept 1 day | — |
| A beta build | usable for 90 days after its tag | a blocking notice |
| Two CI builds, and the owner's rebuild | byte-identical | the release fails, or `sign_release.sh` refuses |
| A signature | one touch and a PIN or user verification per signature; the count announced first | `sign_release.sh` aborts on an extra request |
| Keys in CI, the repository or a cloud service | none | a failing review; the key is revoked and replaced |
| A signing key without a backup token | none | the key is not used |

## Interface

```
.github/workflows/release.yml     the jobs release and verify (R1, R3, R7, R9)
.github/allowed_signers            the release keys (R1, R5)
docs/release-keys.md               every key and backup, fingerprints, dates, history (R5)
scripts/release_env.sh             the path remaps and deterministic settings (R2)
scripts/sign_release.sh            R6, run by the owner from his own verified copy
scripts/verify_release.sh          R8, run by anyone
deploy/release/Dockerfile          the pinned build container of R6 and R8
vendor/bundler/                    the bundlers' tools with their SHA-256 (R2)
```

`unsigned-hashes.txt` (R3): one line `<sha256>  unsigned/<name>` per artefact. `SHA256SUMS` (R6): `# <tag> <full commit SHA>`, then `<sha256>  unsigned/<name>` and `<sha256>  signed/<name>` lines, then `<sha256>  input/libsodium-1.0.22-stable-msvc.zip`. `ROTATION-<date>.txt` and its `.sig` (R5): a key change signed by a key still listed.

**PR slices** (AGENTS 14): (a) `release_env.sh`, the vendored bundler tools, the double build of the server and the Linux desktop (R2, R3 for them); (b) Android, macOS, Windows and iOS unsigned builds (R3 for them, R4); (c) the keys document, the allowed signers and `sign_release.sh` (R1, R5, R6); (d) `verify_release.sh`, the `verify` job and the APK check (R7–R9); (e) the fingerprint publication and the amendments (R10, R11).

## Security

- A changed binary cannot pass for a release. The owner signs only what matches his own rebuild from the signed tag, on hosts outside GitHub, for every platform he ships, Windows included (R6, O-Q5), so a compromised CI runner, Action or GitHub account cannot slip a different artefact past the signature. The manifest names its tag and commit (R6), so an old signed manifest cannot be passed off as a new release.
- The owner verifies the tag with his own signers file and runs his own copy of the signing script (R6), so a rewritten tag chain or a changed script in the repository does not steer what he signs.
- A third party's first check needs nothing from the repository (R8), against a fingerprint published outside GitHub and the landing host (R10), and a public release's manifest is in a log nobody can rewrite (O-Q6), so an attacker who holds GitHub and the landing host cannot show even one person a forged release.
- rc builds carry no production signature and say "RC", and beta builds say "Beta" and expire (R2, R7), so neither can pass for a public release or stay in use after it.
- Reproducibility proves that a binary matches its source and its pinned toolchain and dependencies. It does not prove they are honest: a compromised toolchain, or a malicious version of a locked dependency, builds the same wrong binary every time. Review of dependency changes is what covers that (AGENTS 8).
- The iOS app installed from the App Store cannot be compared with a rebuild, only its unsigned archive (R4); a documented residual.
- The macOS and Windows artefacts can be compared only on their own build hosts, and a Linux verifier reports them `unchecked` (R4, R8); a documented residual.
- The Windows desktop runs a libsodium binary built by libsodium's author (R4, spec 042-connection-host R15); a documented residual.
- The first release's tag is checked against its own signers file (R1); a documented residual, which the owner's own check of R6 covers.
- A key lost with its backup cannot be replaced for Android installs in place, whose users would reinstall and lose their channels (spec 053-device-security); a documented residual, which the backup token and the v3 lineage exist to avoid.
- Malware on the owner's signing machine can swap what a touch the owner expects signs; the announced touch count, the printed manifest hash and the check on a second machine (R6) narrow it; a documented residual.
- Releases need the owner, so a client fix waits for them (`.github/SECURITY.md` says so); a documented residual.

## Test cases

- T01 (covers R1): `check_s060_t01_r01_tags` in CI: a tag signed by a key absent from the `allowed_signers` of the highest-version ancestor `v*` tag stops both jobs; a lightweight tag, a tag not on an allowed branch, and a `review-1` tag start no job; a real tag passes; the repository's rulesets cover `v*` and `review-*`.
- T02 (covers R2): `check_s060_t02_r02_deterministic_inputs`: the workflow sources `release_env.sh`, builds with `--locked` and network disabled after resolution; the check fails when libsodium's `optimized` feature or `CFLAGS` is set, when a bundler tool lacks its SHA-256, or when a base image has no digest; the version function gives, for `v1.2.3-rc.4`, `v1.2.3-beta.2` and `v1.2.3` on ABI 1, the codes 10203041, 10203321 and 10203991, in rising order; a beta build dated 91 days after its tag shows the blocking notice.
- T03 (covers R3): CI step `s060_t03_r03_double_build`: the two builds of each artefact compare equal and `unsigned-hashes.txt` lists them; the only run artefact is `unsigned-hashes.txt`, with a 1-day retention; a fixture artefact with one byte changed fails the step.
- T04 (covers R4): `check_s060_t04_r04_residuals`: `SHA256SUMS` of a test release lists the libsodium input and the iOS archive; the Security section names every residual of R4.
- T05 (covers R5): `check_s060_t05_r05_keys`: no workflow references a signing secret; no private key or keystore file is in the repository; every key that `docs/release-keys.md` lists has a backup and a `SHA256:` fingerprint, the file names the backups' place, and it agrees with `.github/allowed_signers`; the Google app-signing certificate differs from the Android signing key's; a manifest signed by a retired key and absent from its list is rejected by `verify_release.sh`.
- T06 (covers R6): `s060_t06_r06_sign_release`: a `vX.Y.Z` test tag logs its manifest in a test Rekor before any upload; the Windows step asks for the three signatures it announced; with fake signers and a fake CI hash file, a local rebuild that differs from CI's stops the script before signing; the written `SHA256SUMS` starts with the tag and commit line, lists both hashes of every artefact, and verifies with the fake key; every tag leaves the GitHub release a draft; a tag that fails the owner's own signers file stops the script before it runs anything from the checkout; an unrebuilt line of the CI hash file is refused; without the Windows host the release omits Windows and nothing else; an extra touch request aborts; an `-rc.N` tag uploads nothing to App Store Connect.
- T07 (covers R7): CI step `s060_t07_r07_apksigcopier`: `apksigcopier compare` passes on the signed APK and the rebuild, and fails on an APK rebuilt from a changed source; an `-rc.N` build shows "RC", its APK is signed by the test key, and its manifest verifies only under `privatechat-rc`.

## Vectors

None.

## Acceptance criterion

The jobs `release` and `verify` (started by the owner) green for a `vX.Y.Z-rc.1` tag, left as a draft release; `scripts/sign_release.sh` run by the owner with the tokens and `scripts/verify_release.sh` run by a second person from a clean clone both succeed. Non-automatable: the backup tokens are enrolled and sealed in their named place, the Windows virtual machine rebuilds the Windows artefacts, and the fingerprint is published as R10 says.

## Out of scope

- Google Play, F-Droid and the public release's distribution (spec 064-public-release).
- Automatic updates inside the apps: v1 is updated through the stores and by downloading a new installer.
- Building libsodium from source on Windows (a later change, spec 042-connection-host R15).

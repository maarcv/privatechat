# 053 — Device security: the storage key, the app lock and the device measures of §8

Status: draft
Phase: 5
Related ADRs: 0020, 0021, 0028, 0037, 0041
Depends on: 020-store-files, 027-core-api, 040-uniffi, 041-desktop-bridge, 042-connection-host
Blocks: 050-desktop-mvp, 051-android-mvp, 052-ios-mvp, 054-qr-invite, 056-chat-screens
Human reviewer: Marc Vilardebó · Accepted on: —

## Context

`docs/spec.md` §8 lists the measures that protect a device: where the storage key `K_db` lives and what unwraps it, when the app locks, what is kept out of backups, screenshots, notifications, the clipboard, the keyboard and the build flags. This spec turns that table into requirements, one mechanism per platform, so that the three UI specs (050, 051, 052) build on one definition of "locked" and "unlocked". The desktop's keychain entry, its lock routine and its web view already live in spec 041-desktop-bridge; this spec adds what 041 left to it (the operating system's authentication at unlock, when the app locks on its own, notifications, the clipboard) and references the rest.

Before drafting, the human reviewer decided on 2026-09-26 (`docs/audit-log.md`, "Phase 5 drafts"): every desktop unlock asks the operating system's user authentication where one exists (Q2), local notifications exist on the desktop only (Q4), and Android starts at API 30 (Q5). During audit M the reviewer decided that a system screen the app opens itself does not lock it for up to 120 s (M-Q1), and that an iOS screenshot is a residual the app reacts to (M-Q2) (`docs/audit-log.md`, "Audit M").

**In plain words.** Everything the app keeps on a device is encrypted with one 32-byte key. On a phone, that key is itself locked by the phone's secure chip, and only the phone's own fingerprint, face or PIN prompt can open it; on a computer, it sits in the system keychain, and the system's Touch ID, Windows Hello or password prompt must be passed before the app reads it. "Locked" means the key has been wiped from memory, the files are closed, the screens hold nothing, and the app is offline; the app locks when it goes to the background, when the screen turns off, when the computer's session locks, or when the user asks. The one exception is a system screen the app opened itself, such as the file picker, for up to two minutes. Nothing the app holds goes into backups, notification texts or logs, and nothing is sent to any analytics service. On an iPhone a screenshot cannot be prevented, so the app hides the secret on screen and warns at once.

## Requirements

**The storage key on Android**

- R1 `platform/StorageKey.kt` MUST keep `K_db` as the AES-GCM encryption, under one Android Keystore key, of 32 bytes drawn with `Core.generateStorageKey` (spec 040-uniffi R8). The Keystore key MUST be an AES key of 256 bits with block mode GCM, no padding, `setUserAuthenticationRequired(true)` (without which the Keystore adds no authentication requirement at all and ignores the next call), `setUserAuthenticationParameters(t, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)` where `t` is the grace of R7, `setInvalidatedByBiometricEnrollment(false)`, `setUnlockedDeviceRequired(true)` only on API 35 and later (it has known defects on API 31–34, and the locks of R8 already cover it), and `setIsStrongBoxBacked(true)` when `PackageManager.FEATURE_STRONGBOX_KEYSTORE` is present (a `StrongBoxUnavailableException` falls back to the TEE once, at creation). There are two key aliases, `storage-key-a` and `storage-key-b`. The wrapped key MUST be the file `noBackupFilesDir/storage-key.wrap`, holding one generation byte (`a` or `b`, naming the alias that wraps it), the 12-byte IV, and the ciphertext with its 16-byte tag, written with a temporary file and a rename. Next to it, the non-secret file `noBackupFilesDir/storage-key.grace` holds the configured grace as 4 bytes, written after every successful save of `lock_timeout_seconds`, so that R7's check can run before `Core.open`. The unwrapped bytes go once to `Core.open`, which zeroes them (spec 040-uniffi R9), after R7's check has used them. The class exposes exactly `create(activity)`, `unwrap(activity)` and `rewrap(activity, graceSeconds)` of the Interface.

**The storage key on iOS**

- R2 `Platform/StorageKey.swift` MUST keep `K_db` as the encryption, under one P-256 key in the Secure Enclave, of 32 bytes drawn with `Core.generateStorageKey`. The Secure Enclave key MUST be created with `kSecAttrTokenIDSecureEnclave`, `SecAccessControl(kSecAttrAccessibleWhenUnlockedThisDeviceOnly, [.privateKeyUsage, .userPresence])`, and a fixed application tag. The 32 bytes are encrypted with `SecKeyCreateEncryptedData` and `.eciesEncryptionCofactorVariableIVX963SHA256AESGCM` to the key's public half (measured on 2026-09-26: 113 bytes for 32), and the ciphertext is one Keychain generic-password item, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, so that neither leaves the device or reaches an iCloud backup. Decryption passes the `LAContext` that `LockController` holds (R7) as `kSecUseAuthenticationContext`. The class exposes exactly `create()` and `unwrap(context:)` of the Interface. This wrapping is the operating system's own cryptography, which §8 mandates; it touches only `K_db`, never a channel key or the wire format (AGENTS 2).

**The storage key on the desktop**

- R3 On macOS the entry of spec 041-desktop-bridge R16 MUST be a data-protection Keychain item written through the `security-framework` crate with its `OSX_10_15` feature (for `PasswordOptions::use_protected_keychain`, which compiles without `unsafe`), the access control `USER_PRESENCE` and `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, in place of `keyring`'s macOS store, so that reading it makes the system ask for Touch ID or the account password before it returns the key. The item keeps 041 R16's service and user. The prompt's text is the system's: the crate offers no safe setter for `kSecUseOperationPrompt`. Results map as follows: `errSecUserCanceled` (−128) and `errSecAuthFailed` → `Cancelled`; `errSecInteractionNotAllowed` → `KeychainUnavailable`; `errSecMissingEntitlement` (−34018), which every build not signed with a team certificate and a provisioning profile gets (measured on 2026-09-26: an unsigned binary gets −34018, and an ad-hoc build with the `keychain-access-groups` entitlement is killed at launch) → a release build refuses to start with the fixed text of R19, and only a debug build compiled with the cargo feature `dev-login-keychain` falls back to `keyring`'s login-keychain item and spec 041-desktop-bridge's `Unlock` confirmation. The fallback is compiled only under `cfg(all(debug_assertions, feature = "dev-login-keychain"))`, and `key.rs` holds `#[cfg(all(feature = "dev-login-keychain", not(debug_assertions)))] compile_error!(…)`, so that no release binary can carry it, whoever builds it; a debug build without the feature refuses to start as a release does. While the fallback is in use, the app shows a persistent banner with the fixed text of R19, "Development build: the storage key is not protected.", on every screen.
- R4 On Windows every `unlock` MUST first ask `Windows.Security.Credentials.UI.UserConsentVerifier::RequestVerificationAsync` (the `windows` crate's WinRT projection, awaited through `windows-future` with its `std` feature, with no `unsafe`), with the fixed text of R19, and read the Credential Manager entry of spec 041-desktop-bridge R16 only after `Verified`. `Canceled`, `RetriesExhausted` or any other result returns `Cancelled` with nothing read. When the data directory holds no data (the test of spec 041-desktop-bridge R15, which reads no keychain entry, so nothing is read before `Verified`), the app first calls `CheckAvailabilityAsync`: when it gives `DeviceNotPresent` or `NotConfiguredForUser`, the app writes the non-secret file `app_local_data_dir()/presence.none` and asks 041's confirmation in place of `RequestVerificationAsync`, so that a computer without Windows Hello can create its key; otherwise it asks `RequestVerificationAsync` as above. Every `unlock` whose availability check gives `Available` removes `presence.none`, so that a computer where Windows Hello was set up and later removed returns `Cancelled` rather than the fallback. `unlock` falls back to the native confirmation of spec 041-desktop-bridge R9 and R16 only when that file exists and the check still gives one of those two results; any other unavailability (`DeviceBusy`, `DisabledByPolicy`, a check that turns unavailable after Windows Hello was present) returns `Cancelled`. On Linux, where no standard equivalent exists, `unlock` keeps 041's confirmation. On macOS and Windows, where the system prompt asks for the user, it replaces 041's `Unlock` confirmation, and it is asked at every `unlock`, the first of the process included.

**Unlocking**

- R5 On Android and iOS, `unlock` MUST follow the rules of spec 041-desktop-bridge R16 for the key's presence, with the wrapped key (R1, R2) in place of the keychain entry and the same meaning of "holds data" (041 R15), and return an `UnlockResult` of the Interface, checking the rows in this order:
  - Any tombstone of R23 is deleted first.
  - The directory holds data, and the wrapped key or the platform key is missing, or the platform reports the key permanently invalidated (`KeyPermanentlyInvalidatedException` at `Cipher.init` on Android, which needs no prompt; on iOS `errSecItemNotFound` for the Secure Enclave key or the item, but only while `isProtectedDataAvailable` is true and a second query gives the same answer): `KeyLost`, and create nothing. This row comes before the next, so that a user who removed the screen lock learns at once that the history is lost, rather than after setting a new one.
  - No device credential is set (`KeyguardManager.isDeviceSecure` false on Android; `canEvaluatePolicy` failing with `passcodeNotSet` on iOS): `Unavailable`, with the fixed text "Set a screen lock (PIN or passcode) to use this app" of R19 and an action that opens the system settings, and nothing created.
  - A wrapped key and a platform key that decrypts it, and the directory holds data: open; `Unlocked`.
  - The directory holds no data: delete any wrapped key and platform key, create both (R1, R2), unwrap the new key once to check it, and open; `Unlocked`.
  - The prompt was cancelled, failed or timed out: `Cancelled`. On Android, a `UserNotAuthenticatedException` at `Cipher.init` while the app believed it was within the grace (the Keystore counts from its own authentication token, which is slightly earlier) is treated as outside the grace: the prompt is shown, never `Transient`. Any other platform error, the iOS query of the previous row while protected data is unavailable or the two queries disagree included: `Transient`. Both stay locked and create nothing: no transient failure ever draws a new key (`docs/spec.md` §8 "Loss of the wrapping key").
  - `Core.open` fails: `Failed` with its `FfiError`, and the unwrapped key is zeroed.
  After `KeyLost` the app offers only `reset()` (R23), behind a destructive confirmation whose fixed text (R19) says that the local history is lost, that each channel comes back by importing a new invitation (`docs/spec.md` §7 "Leave channel", §8), and that the user's old keys stay valid for the others, so the members of each channel should be asked to mark the old key as retired (§7 "Key regeneration").
- R6 The app lock MUST be the operating system's prompt and nothing else, with no app PIN or password: `BiometricPrompt` with `BIOMETRIC_STRONG or DEVICE_CREDENTIAL` on Android, hosted by a `FragmentActivity`; an `LAContext` evaluating `.deviceOwnerAuthentication` on iOS; and R3 and R4 on the desktop. The prompt's title and reason are fixed texts of R19 that name no channel, except on macOS, where the system writes the Keychain prompt's text (R3).
- R7 `lock_timeout_seconds` (spec 027-core-api R13, default 60, 0..=86 400) MUST be the grace within which an `unlock` skips the in-app prompt, with one definition on both phones: fewer than that many seconds have passed since the last successful in-app prompt, a time `LockController` keeps in memory only (a new process always prompts). Outside the grace the prompt is always shown, whatever the platform would allow. `0` is the "strict" option of §8: every `unlock` prompts. "Lock now" (R10) clears the time, so that the next `unlock` prompts. The grace never keeps the device unlocked: the locks of R8 always happen, only the next prompt is skipped. While `settings_reason` is `Some(UnsupportedVersion)` (spec 027-core-api R2), where a setter changes memory only, "Lock after" is disabled on every platform (spec 056-chat-screens shows it under its banner), so that no re-wrap and no write of `storage-key.grace` happen for a setting that is not saved.
  - Android: the Keystore key's `t` (R1) equals the grace and is its upper bound, since the Keystore authorises a timed key after any authentication of the device, the lock screen's included. A re-wrap runs inside the queue of R9 and MUST: create the other alias with the new `t`; encrypt `K_db` under it; write `storage-key.wrap` with the new generation byte through a temporary file and a rename. The old alias is deleted only after the next `unlock` succeeds under the new generation. `unwrap` tries the alias the generation byte names, so a crash at any step leaves one wrap and its key. There are two paths:
    - A change of the setting, made while unlocked: the app prompts, unwraps `K_db` into an array that `LockController` owns, re-wraps, zeroes that array (these bytes never go to `Core.open`, which already holds its own copy), then saves the setting with `set_lock_timeout_seconds` on the open `Core`, and only then writes `storage-key.grace` and the in-memory grace.
    - The check at `unlock`: after the prompt and before `Core.open`, when `t` (`KeyInfo.userAuthenticationValidityDurationSeconds`, readable with no prompt) differs from `storage-key.grace`, the app re-wraps with the bytes this `unlock` has just unwrapped to the file's value, in either direction, and saves no setting: the file is written only after the setting is saved, or from `settings()` after `Core.open`, so it is never ahead of the setting. Until `Core.open` the in-memory grace is the smaller of the file and `t`. After `Core.open`, `settings().lock_timeout_seconds` is the one source: the in-memory grace is set from it, `storage-key.grace` is rewritten from it when it differs, and a key whose `t` then differs from it is re-wrapped to it at the next `unlock`.
  - Before `Core.open`, the in-memory grace is the smaller of `storage-key.grace` and `t`. A missing or invalid `storage-key.grace` (outside 0..=86 400, not 4 bytes) skips the check and counts as a grace of 0. At the first creation of the key and after `reset()` (R23), when no file exists yet, `create` uses the default of spec 027-core-api R13 (60 s), the check is skipped, and the file is written from `settings()` once `Core.open` has returned. A crash between the save of the setting and the write of the file therefore relaxes nothing: the next `unlock` uses the smaller value until the setting is read.
  - Prompts: unwrapping costs one prompt outside the grace; encrypting under a new key with `t = 0` costs one more (a `CryptoObject`); encrypting under a new key with `t > 0` costs none when the Keystore accepts the authentication just made, and one otherwise (053-R7). So a change of the setting to 0 costs two prompts, any other change one or two, and the check at `unlock` at most one more than the unlock itself.
  - iOS: `LockController` keeps the evaluated `LAContext` and invalidates it (`invalidate()`) once the grace has passed since the prompt; within the grace, `unwrap(context:)` decrypts with it and shows no prompt.
  - Desktop: no grace; every `unlock` prompts (R3, R4, Q2).
- R8 The app MUST lock (`Core.lock` on mobile, spec 040-uniffi, and the lock of spec 041-desktop-bridge R17 on the desktop, both running the lock routine of spec 042-connection-host R12) on each of these events:
  - Android: `ProcessLifecycleOwner` `ON_STOP`; `ACTION_SCREEN_OFF`; "Lock now". While a system screen the app itself started for a result is in front (the document pickers of spec 054-qr-invite, its share chooser, the camera permission's settings screen, and the device-credential screen of `BiometricPrompt`), `ON_STOP` does not lock for up to 120 000 ms after that screen started; the app locks when that time runs out before it is back, and screen-off always locks (decided with the human reviewer, `docs/audit-log.md`, "Audit M", M-Q1): an `ACTION_SCREEN_OFF` delivered late to a process that was frozen, whose event time falls inside the exception, locks at once even after the first frame has been drawn.
  - iOS: `sceneDidEnterBackground`; `protectedDataWillBecomeUnavailable`; "Lock now". The same exception applies to the document pickers (the file picker and the folder picker) and the share sheet of spec 054-qr-invite, if they move the scene to the background, for `min(120 000 ms, the background time the system grants)`: while it runs, a `beginBackgroundTask` is held, and a timer starts the lock when `UIApplication.backgroundTimeRemaining` falls below 10 s; the task's expiration handler only ends the task, since a lock started there gets no time to run.
  - On both phones the exception's end is a check at the return, not only a timer: a frozen (Android 14 and later) or suspended (iOS) process runs no timer and gets the screen-off broadcast late. At `ON_START` and `sceneWillEnterForeground`, while an exception is running, the app locks before its first frame is drawn when at least 120 000 ms of a monotonic clock (`SystemClock.elapsedRealtime`, `ContinuousClock`) have passed since the system screen started, or when the device slept in between (on Android, the gap between `elapsedRealtime` and `uptimeMillis` grew). The timer is kept as a best effort.
  - Desktop: the main window unfocused for `lock_timeout_seconds` (0: at once), where the time a dialog or prompt the bridge itself opened is in front (the dialogs of spec 041-desktop-bridge R9 and R6, and the prompts of R3 and R4) does not count, for at most 120 000 ms and only while that dialog itself has the focus: once 120 000 ms have passed, or the dialog loses the focus to another application, the unfocused time counts again, and when the lock comes the lock routine closes the dialog where the platform allows it (any answer after that returns `Locked`, 041 R9). The session lock itself locks at once on Linux: the app resolves its session's object path with logind's `Manager.GetSession("auto")` (a proxy on `session/auto` never receives the signals) and watches that path's `LockedHint` becoming true (`PropertiesChanged`, through `zbus`, already in the tree) and its `Lock` signal; `LockedHint` is set only by screen lockers that call `SetLockedHint`, and with any other locker the focus timer applies. On macOS and Windows the session-lock notifications are reachable only through `unsafe` calls (measured on 2026-09-26: `NSDistributedNotificationCenter`'s observers in `objc2-foundation` and `WTSRegisterSessionNotification` in `windows` are `unsafe`), so the focus timer alone applies there. The desktop also locks when the system goes to sleep (on Linux, logind's `Manager.PrepareForSleep(true)`, through `zbus`), and the timer measures both a monotonic clock (`Instant`, which stops during a suspend on macOS and Linux) and the wall clock (`SystemTime`, which jumps forward at wake): it locks when either shows the timeout has passed, so a laptop that slept longer than the timeout is locked at wake, before it reconnects. While the device is unlocked, focused or not, a heartbeat tick every 1 000 ms locks when the wall clock, or on macOS and Linux the gap between the wall clock and the monotonic clock, advanced by more than the timeout since the previous tick, so that a window focused when the lid closed is locked at wake; the connection host asks `Sink::before_connect` before it opens any socket (spec 042-connection-host R9), and the bridge runs the same check there: when it trips, it spawns the lock as a task of its own and returns `false` at once, since an inline lock would wait for the very plan task that asked (spec 041-desktop-bridge R7). On Linux the app holds a logind `delay` inhibitor for `sleep` while unlocked and releases it once the lock routine has run after `PrepareForSleep(true)`, so the lock happens before the suspend. The prompts of R3 and R4 follow the focus rule of spec 041-desktop-bridge R9, and the `Locked` page never calls `unlock` without a user action (a requirement on spec 050-desktop-mvp), so that a lock by the timer never raises Touch ID or Windows Hello over another application. Also "Lock now" and quit (041 R17).
  Locked is disconnected: no socket stays open and no work runs in the background (`docs/spec.md` §8 "Background"). A desktop window that stays focused while nobody uses it does not lock: the app cannot count input, since the web view's input events are untrusted and a script could fake them, so the operating system's own screen lock is the defence, which the help recommends. That is a documented residual, as is a frozen or suspended phone process that keeps `K_db` in memory past the 120 s until it returns or is killed.
- R9 On Android and iOS, one `LockController` per app MUST serialise lock, unlock, reset and the re-wrap of R7 as spec 041-desktop-bridge R15 does: a first-in, first-out queue held for the whole of each, never across a prompt, with every `Core.open` awaiting the last `Core.lock` (spec 040-uniffi R9), on top of the connection host's own lifecycle lock (spec 042-connection-host R4). An `unlock` while unlocked returns at once; a lock requested while a prompt is open dismisses the prompt's result and locks. A `locked` callback of the current generation that `LockController` did not start (a fault lock of spec 042-connection-host R7) is a lock all the same: it queues a lock whose `Core.lock` finds nothing open and does nothing, so that the controller marks itself locked, stops the network monitor of specs 051 and 052 and drops the view models, and the next `unlock` really opens. `Core` is the phones' one generation filter (spec 040-uniffi R9); the controller and the apps filter nothing. Every lock drops every view model's data at its start, on the main thread, before `Core.lock` is called (R21), so that a lock the system suspends half-way leaves no content on screen or in the view models, and runs to its end even when the app leaves the foreground meanwhile: on iOS inside a `beginBackgroundTask` begun before `Core.lock` and ended when `Core.lock` returns (`Core` delivers that lock's `locked` itself, spec 040-uniffi R9) (a suspended lock would keep `K_db` in memory and flush after `.complete` protection shut the files), and on Android launched in the application's scope, never in a scope that the lifecycle cancels.
- R10 "Lock now" MUST exist as an in-app action on every screen of 050, 051 and 052, and as a menu item with the accelerator `CmdOrCtrl+L` on the desktop. There is no launcher shortcut and no home-screen quick action: they can only be used while the app is already locked. "Lock now" also ends the grace (R7).

**Storage, backups and screens**

- R11 The data directory MUST be kept out of backups and device transfer:
  - Android: `noBackupFilesDir/data`, with `android:allowBackup="false"`, `android:fullBackupContent="false"` and `dataExtractionRules` that exclude every domain from `cloud-backup` and `device-transfer`.
  - iOS: `Application Support/data`, with `isExcludedFromBackup = true` and the file protection `.complete`, so that its files cannot be read while the device is locked.
  - Desktop: spec 041-desktop-bridge R15 (the macOS attribute); on Windows and Linux the data lives outside the user's sync folders, and the help says that File History and similar tools should exclude it.
  A restore onto another device therefore brings back no data directory and no wrapped key, and the app starts empty (R5's "holds no data" row), never with `KeyLost`.
- R12 Screens MUST NOT be captured where the platform allows it:
  - Android: `FLAG_SECURE` on the one activity, and `SecureFlagPolicy.SecureOn` on every Compose `Dialog`, `Popup`, `DropdownMenu` and `ModalBottomSheet`, since each is a window of its own that the activity's flag does not reach. The invitation QR, the export password and the 12 words are only ever drawn on full screens of the activity window (specs 054-qr-invite, 055-verify-ui).
  - iOS: an opaque cover over the whole window on `sceneWillResignActive` and while the window scene's `traitCollection.sceneCaptureState` is `.active` (observed with `registerForTraitChanges`), removed on `sceneDidBecomeActive` when it is not. A screenshot cannot be blocked: on `UIApplication.userDidTakeScreenshotNotification`, a screen that shows a secret hides it at once and shows the warning of spec 054-qr-invite, a documented residual (M-Q2).
  - Desktop: the one window is created with `contentProtected: true`, which excludes it from capture on Windows 10 2004 and later (`WDA_EXCLUDEFROMCAPTURE`) and on macOS as far as the system honours it (`NSWindow.sharingType = .none`); on Linux nothing, and the help says so.
- R13 Local notifications MUST exist on the desktop only (Q4). A click on one MUST focus the running main window: on macOS through `notify-rust`'s response, on Windows through an activation callback or, where `notify-rust` registers none for an unpackaged app, a second instance started by the click that hands over to the first (041 R15's `instance.lock`) and exits (053-R13). While the device is unlocked and the main window is not focused, a `core-event` `Message` from a peer that is not muted raises one notification whose title is the app name and whose body is the fixed text "New messages" of R19, at most one every 60 000 ms, through the `notify-rust` crate from the Rust side (not `tauri-plugin-notification`, which brings a banned `rand`), with no channel, peer, count or content. The bridge's `Sink` only adds (channel, peer) to a coalescing set and wakes a separate task, which takes the whole set, reads whether each peer is muted through `Host::call(peers)`, and calls `notify-rust` off the connection host's threads when any member of the set is not muted (spec 041-desktop-bridge R7); the 60 000 ms window starts only when a notification is shown, so a batch of muted senders uses none of it; the focus is read from an `AtomicBool` that the window's focus events update, since `notify-rust` blocks on D-Bus and on the click's response and the host calls its `Sink` under its lock (spec 042-connection-host R5). Before the first notification the app calls `notify_rust::set_application(<its bundle identifier>)` on macOS, and passes `.app_id(<the AppUserModelID its installer registers>)` on Windows, so that the notification shows under the app and a click focuses its main window, not Finder or PowerShell (measured on 2026-09-26: the defaults post as those). On macOS the crate's backend replaces `-[NSBundle bundleIdentifier]` for the main bundle process-wide; nothing else in the app reads it, and that side effect is stated here. Since the app locks once the window has been unfocused for `lock_timeout_seconds` (R8), notifications only cover that time after the user leaves the window, and none with `0`; the help says so. Android and iOS MUST NOT request notification permission (`POST_NOTIFICATIONS`, `UNUserNotificationCenter`) and post none.
- R14 The clipboard MUST hold only what the user copied from a message, and only briefly; an invitation text, a `.chatcfg` password and the export password MUST NOT be copied by any action of the app. Leaving the app does not clear the clipboard, so that a copied message can be pasted in another app; it is cleared 60 000 ms after the copy, and at once by "Lock now", screen-off and a session lock (decided with the human reviewer, `docs/audit-log.md`, "Audit M", M-Q5). Message text MUST NOT be selectable by the platform's own text selection on any platform (no `SelectionContainer` on Android, no selectable `Text` on iOS, `user-select: none` on the desktop), so that the only copy is the app's "Copy" action; on the desktop the page also intercepts the `copy` event and the Edit menu's Copy and routes them to `copy_message` for the row that has the keyboard focus, and does nothing when no text row has it (a requirement on spec 050-desktop-mvp). Row keys follow one stable rule (spec 056-chat-screens R7): when a `server_id` repeats, the own row keeps its `s:` key and the row that arrived later is keyed by position, so that a key never moves from one row to another; the copy command does not depend on that key, since an own row is copied by its `client_ref`.
  - Android: the clip carries `ClipDescription.EXTRA_IS_SENSITIVE` (which hides its preview from API 33; no effect on API 30–32) and a fixed label that names nothing. While the app is in the foreground, a timer clears it (`clearPrimaryClip`) 60 000 ms after the copy when the clip still carries its label; otherwise the app clears it at the next foreground when the clip still carries its label and is older than 60 000 ms, since a background app cannot read the clipboard, and at once on "Lock now" and screen-off while it is in the foreground (053-R14). Otherwise Android's own clearing (API 33 and later) applies, a documented residual.
  - iOS: `UIPasteboard.setItems(_, options: [.localOnly: true, .expirationDate: now + 60 s])`; "Lock now" and screen-off clear it at once when it still holds the app's item (`changeCount` unchanged).
  - Desktop: the Rust command `copy_message(channel, kind, id)`, where `kind` is `Server` or `Client` and `id` a `server_id` or a `client_ref`: an own row is always copied as `Client` with its `client_ref`, which a delivered own `Message` keeps, and `Client` matches only own rows; `Server` is for peers' rows and matches them by `server_id`. The bridge reads the body from `messages(channel)` itself, so the page never passes the text and a script cannot put a text of its choice on the clipboard; when more than one row matches (a server that repeats a `server_id`), it copies nothing, so that a server cannot steer which body is copied; it returns `UnknownChannel` for an unknown channel and does nothing for a key with no text row. The page offers no "Copy" on a row keyed by position (spec 056-chat-screens R7). It is served by one clipboard task that owns a single `arboard::Clipboard` for the life of the process (`arboard` with `default-features = false`, text only; its default `image-data` feature brings banned image crates, measured) and receives messages from `copy_message`, from its 60 000 ms timer, which the lock routine does not abort, and from "Lock now", a session lock and quit, which clear the clipboard at once when it still holds the copied text (the same counter or hash check), retrying on `ClipboardOccupied`, since Windows allows one thread at a time on the clipboard. It writes with `exclude_from_cloud`, `exclude_from_history` and `exclude_from_monitoring` on Windows and `exclude_from_history` on macOS and Linux, so the text reaches neither Windows' cloud clipboard nor the clipboard histories that honour those markers. Once written, the task keeps no copy of the text: to know whether the clipboard still holds it, it keeps the clipboard's change counter where one is reachable without `unsafe` (`NSPasteboard.changeCount` through `objc2-app-kit` on macOS, the clipboard sequence number on Windows if a safe binding exists), and otherwise a 64-bit keyed hash of the text (`std::hash::RandomState`, keyed per process) and its length. The counter, hash and length are forgotten once the timer or a clearing has run, whatever the result. Reading the clipboard to compare a hash may raise macOS's alert on programmatic pasteboard reads (to be measured, 053-R14), which the change counter avoids. `arboard`'s Windows crates are BSL-1.0, which spec 041-desktop-bridge R2's licence list gains (R20). On Linux the copied text is served by the app itself, so its availability to other apps depends on the compositor; the help says so. macOS Universal Clipboard is not excluded (`arboard` exposes no switch for it), a documented residual.
- R15 Text entry MUST follow §8 "Keyboard":
  - Android: the `.chatcfg` and export password fields are Compose text fields with `KeyboardType.Password`, auto-correction off, and `IME_FLAG_NO_PERSONALIZED_LEARNING` set through `InterceptPlatformTextInput` (Compose sets no such flag itself, and always sets `IME_FLAG_NO_FULLSCREEN`, which stands for `flagNoExtractUi`); the message composer gets the same flag and auto-correction off, so the keyboard learns no message text. While a password field is shown, the window's root view is `IMPORTANT_FOR_AUTOFILL_NO_EXCLUDE_DESCENDANTS`, so no autofill service offers to save the password. The app shows a one-time warning when the default input method (`Settings.Secure.DEFAULT_INPUT_METHOD`) is not a system app.
  - iOS: password fields are `SecureField` with `textContentType` nil (never `.password`), the composer has `autocorrectionDisabled()` and spell checking off, and the app refuses custom keyboards (`application(_:shouldAllowExtensionPointIdentifier:)` returns `false` for `.keyboard`, through the app delegate adaptor).
  A Compose or SwiftUI text field holds its text as a `String`, so the field's text is copied into bytes on submit, handed over as spec 040-uniffi R9 says, and the field is cleared; the `String` itself is not zeroed, a documented residual.

## Limits

| Input | Range | Out of range |
| --- | --- | --- |
| `K_db` | exactly 32 bytes | `KeyLost` |
| `storage-key.wrap` | 1 + 12 + 32 + 16 bytes | `KeyLost` when the directory holds data |
| `storage-key.grace` | 4 bytes, 0..=86 400 | the check skipped and a grace of 0 until `Core.open`; rewritten from the setting after it |
| `lock_timeout_seconds` | 0..=86 400 (spec 020-store-files) | `BadConfig` from the core |
| Grace after an in-app prompt | before `Core.open`, the smaller of the file and `t`; after it, `lock_timeout_seconds`; in memory; none on the desktop | a new prompt |
| Clipboard after a copy | 60 000 ms; at once on "Lock now", screen-off and a session lock | cleared |
| A system screen the app opened (mobile) | ≤ 120 000 ms of a monotonic clock, checked at the return | locked before the first frame |

| Notifications | at most one per 60 000 ms | dropped |

## Security

- `K_db` is unwrapped only after the operating system's prompt (R1–R4, R6) and lives only in Rust while unlocked; the platform code holds it for one call and zeroes it (spec 040-uniffi R9). On Android and iOS the wrapping key never leaves the secure hardware; on macOS the Keychain enforces user presence; on Windows the prompt is a check the app makes before reading an entry any process of the user can read, and on Linux there is only 041's confirmation. Both are documented residuals of `docs/spec.md` §8 ("within the session, any process of the user can read keychain and files").
- The grace of R7 skips a prompt, never a lock, and counts only from the app's own prompt: a phone unlocked at its lock screen and handed over still prompts in the app outside the grace. On Android the Keystore alone would authorise the key for `t` seconds after any device unlock; the in-memory time of R7 is what makes the app prompt. `0` removes the grace.
- The system-screen exception of R8 keeps the app unlocked behind a picker or share sheet for at most 120 s, and never once the screen-off broadcast is received or the device slept; the check at the return locks before anything is drawn even when a frozen process missed its timer, but such a process keeps `K_db` in memory until it returns or is killed, a documented residual. The desktop's dialog exemption is capped the same way.
- `KeyLost` never draws a new key over data (R5), so a Keystore or Secure Enclave failure costs at most a prompt, and a lost key costs the local history, never silently the files. The re-wrap of R7 keeps a valid wrap and key at every step.
- The file protection `.complete` (R11) keeps iOS files unreadable while the device is locked, even to the app. Locking also empties the screens and view models (R21).
- Notifications carry no content or name (R13), the clipboard holds a copied message briefly and never an invitation or a password (R14), no autofill service sees a password (R15), nothing is logged (R22), and no third-party SDK is linked (R16).
- Documented residuals: a screen that turns off for less than 120 s without the device sleeping, while a frozen process's screen-off broadcast is still queued (R8); a copied message on the clipboard for up to 60 s while the user is in another app (R14, M-Q5); an iOS screenshot of a secret (R12); a focused, unused desktop window (R8); a frozen phone process past the 120 s (R8); the Android clipboard on API 30–32 and after the app leaves the foreground (R14); macOS Universal Clipboard (R14); the `String` of a password field (R15); Linux screen capture (R12); `notify-rust`'s process-wide bundle-identifier replacement on macOS (R13). The warnings of R15 and R18 inform; they do not protect: a rooted device or a third-party keyboard can read what the user types. On Android a process killed during a lock or a send (a low-memory kill after `ON_STOP`) runs no `flush`, losing the cursor and `synced_at` since the last commit, as the desktop's Dock quit does (spec 041-desktop-bridge R17); and a `send` still waiting on the device lock when a lock starts returns `Locked` with nothing committed, its draft dropped with the lock, so a message tapped just before leaving the app may not be sent.
- The desktop copy is excluded from Windows' cloud clipboard and history and from the histories that honour the concealed markers (R14); the keyboard histories, clipboard managers that ignore those markers, and the macOS Notification Center's record of the notification time are outside the app's reach, and the help says so.

## Vectors

None. The core's behaviour is unchanged; the platform measures are checked by the tests above and by hand.

## Acceptance criterion

The tests of each platform green in the CI jobs of specs 050, 051 and 052, and the dependency allowlists green. Non-automatable, on real hardware:
- on an Android phone with StrongBox and on one without, the key is created, the prompt unlocks, a biometric enrolment change keeps the data, removing the screen lock gives `KeyLost`, and after `reset()` `Unavailable` until a screen lock is set, the device-credential screen of `BiometricPrompt` does not lock the app, and a process frozen behind a share target (`am freeze`) and returned after 130 s shows `Locked` before any content;
- on an iPhone, the prompt unlocks, a restore from backup onto another device starts an empty app, the data directory is unreadable while the device is locked, the document pickers and the share sheet keep the scene active or fall within R8's exception, and a screenshot of a shown secret hides it and warns;
- on macOS, reading the entry shows the Touch ID or password prompt, and an unsigned release build refuses to start; on Windows, Windows Hello is asked at every unlock, and the fallback applies only on a machine where it was never set up;
- screenshots and screen recording show nothing of the app on Android, the cover on iOS, and nothing of the window on Windows;
- on Linux, locking the session with a locker that sets `LockedHint` locks the app at once; on macOS and Windows the app locks within `lock_timeout_seconds` of the session lock, by the focus timer;
- the desktop notification says only "New messages", shows under the app's name, and a click on it focuses the main window, on Windows as well (053-R13);
- on each desktop OS, a laptop that sleeps longer than the timeout is locked at wake before it reconnects, and a message copied then pasted in another app is there until 60 s have passed.

## Out of scope

- The screens that show the lock, the prompts' placement and the `KeyLost` flow's layout (specs 050, 051, 052).
- Scanning QR codes, the camera permission's use, and the warning a screenshot of a secret shows (spec 054-qr-invite).
- Reproducible builds, signing and store publication (spec 060-reproducible-builds).
- An app password for a desktop with no keychain (`docs/spec.md` §8): not in v1.

## Open questions

- 053-R4: `RequestVerificationAsync` from a desktop process takes no window handle, so its prompt may open behind the main window; the handle-taking variant, `IUserConsentVerifierInterop::RequestVerificationForWindowAsync`, is a `pub unsafe fn` in `windows` 0.61.3 (measured on 2026-09-26), which spec 041-desktop-bridge R1 forbids. To be measured on Windows before slice (c); the fallback is to accept the placement.
- 053-R7: whether the Android Keystore accepts the authentication just made (a `CryptoObject` prompt on a key with `t = 0`) for a timed key created right after it, which decides whether a re-wrap from 0 to a grace above 0 costs a second prompt. To be measured on a device before slice (a).
- 053-R13: whether `notify-rust` registers an activation for an unpackaged Windows app, so that a click reaches the running window; otherwise the second instance hands over through `instance.lock`. To be measured on Windows before slice (f).
- 053-R14: whether `clearPrimaryClip` works while the app is not focused on Android 10 and later, and whether macOS 15.4 and later alert on the clipboard task's read when no change counter is used. To be measured before slice (e); otherwise the Android clearing happens at the next foreground only.
